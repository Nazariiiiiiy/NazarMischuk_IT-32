# Практика 4. Варіант 1 — Бібліотека

## Завдання 1. Увімкнення перевірки і таблиця-вимір 2
`PRAGMA foreign_keys = ON;` виконано першим рядком сеансу.
Створено таблицю-вимір 2 `readers` (id, full_name, phone, email, registration_date) з `id INTEGER PRIMARY KEY`.

## Завдання 2. Фактова таблиця з двома FOREIGN KEY
Створено фактову таблицю `loans` (id, book_id, reader_id, loan_date, return_date):

- `book_id → books(id)` — **ON DELETE RESTRICT**.
  Книга — це облікова одиниця фонду бібліотеки. Якщо на книгу є записи видач (навіть повернутих), видаляти її не можна: історія видач має зберігати цілісність. Якщо книгу справді треба прибрати з фонду (загублена, списана), для цього має бути окреме поле статусу, а не фізичне видалення рядка.
- `reader_id → readers(id)` — **ON DELETE CASCADE**.
  Читач — це особа, чий обліковий запис може бути видалений (наприклад, за його ж проханням, згідно з політикою збереження персональних даних). У такому разі логічно, щоб і всі його записи видач видалялись разом із ним, а не залишались "осиротілими" рядками з посиланням на неіснуючого читача.

Дії обрано різні навмисно: видалення книги — рідкісна й ризикована операція (втрата історії фонду), тому вона заблокована; видалення читача — штатна операція (право на видалення персональних даних), тому вона каскадна.

## Завдання 3. Заповнення пов'язаними даними
- `readers`: 6 рядків.
- `loans`: 10 рядків, усі `book_id` та `reader_id` посилаються на реальні рядки `books` і `readers` — жодного вигаданого значення.

## Завдання 4. Навмисна помилка зовнішнього ключа
Виконано:
```sql
INSERT INTO loans (book_id, reader_id, loan_date) VALUES (9999, 1, '2026-06-15');
```
Отримано точне повідомлення про помилку:
```
IntegrityError: FOREIGN KEY constraint failed
```
Рядок не було додано до таблиці `loans`, оскільки `book_id = 9999` не існує в таблиці `books`. Це підтверджує, що `PRAGMA foreign_keys = ON;` дійсно активна на з'єднанні.

## Завдання 5. Звірка з ER-діаграмою Практики 3
Таблиця `books` відтворена рівно за офіційним `v1_prerequisites.sql` (id, title, author, publication_year, genre, copies_count). Структура (`books` → `loans` ← `readers`, зв'язки через `book_id` і `reader_id`) відповідає задуманій ER-схемі варіанта "Бібліотека": дві незалежні таблиці-вимірювання і одна фактова таблиця з двома зовнішніми ключами. Змін під час реалізації не було — назви й типи колонок у `readers` та `loans` збігаються з тим, що планувалось.

## Контрольні питання (тези для відповіді)
1. `PRAGMA foreign_keys = ON;` вмикає *перевірку* оголошених FOREIGN KEY на конкретному з'єднанні; SQLite за замовчуванням цю перевірку не виконує, і вона не зберігається між з'єднаннями — тому вмикати треба щоразу заново.
2. `PRIMARY KEY` унікально ідентифікує рядок у "своїй" таблиці; `FOREIGN KEY` — це посилання рядка однієї таблиці на PRIMARY KEY рядка іншої таблиці.
3. `ON DELETE RESTRICT` забороняє видалення батьківського рядка, поки на нього є посилання; `ON DELETE CASCADE` видаляє залежні рядки автоматично разом із батьківським. Вибір залежить від бізнес-сенсу: різні студенти можуть по-різному оцінювати, чи важливіше зберегти історію (RESTRICT), чи автоматично прибрати залежні дані (CASCADE) — обидва варіанти можуть бути обґрунтованими для одного й того ж зв'язку залежно від правил конкретного домену.
