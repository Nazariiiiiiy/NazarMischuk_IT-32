# Практика 15. Створення індексів та аналіз ефективності запитів

Варіант: «Бібліотека». Структура таблиць не змінювалась, додано лише індекси на таблиці `loans`. Версія SQLite, на якій знято плани: 3.45.1. У старіших версіях текст плану трохи інший (наприклад, `SCAN TABLE loans` замість `SCAN loans`).

## Завдання 1. План до індексу

Запит: `SELECT * FROM loans WHERE reader_id = 6;`

План до створення індексу: **`SCAN loans`**. Це означає, що SQLite переглядає всю таблицю рядок за рядком і перевіряє умову в кожному з 10 рядків. У таблиці `loans` на цей момент немає жодного індексу.

## Завдання 2. CREATE INDEX на зовнішньому ключі

Я створив індекс на `reader_id`: `CREATE INDEX idx_loans_reader ON loans(reader_id);`

План після індексу: **`SEARCH loans USING INDEX idx_loans_reader (reader_id=?)`**.

Слово `SCAN` змінилося на `SEARCH ... USING INDEX`. Тепер SQLite не переглядає всю таблицю, а за індексом одразу знаходить рядки з потрібним `reader_id`, як за алфавітним покажчиком у книзі. У дужках видно, за якою умовою працює індекс (`reader_id=?`).

## Завдання 3. Композитний індекс

Запит із двома умовами: `SELECT * FROM loans WHERE reader_id = 6 AND return_date IS NULL;` (неповернуті книги читача 6).

- **До композитного індексу** (є лише `idx_loans_reader`): `SEARCH loans USING INDEX idx_loans_reader (reader_id=?)`.
- **Після** створення `CREATE INDEX idx_loans_reader_returned ON loans(reader_id, return_date)`: `SEARCH loans USING INDEX idx_loans_reader_returned (reader_id=? AND return_date=?)`.

Різниця в дужках: раніше індекс використовував лише одну умову (`reader_id=?`), а другу, про `return_date`, SQLite перевіряв уже вручну в кожному знайденому рядку. Тепер індекс використовує обидві умови (`reader_id=? AND return_date=?`), тож SQLite одразу потрапляє на рядки, які задовольняють обидві. На 10 рядках різниця непомітна, але на великій таблиці в читача можуть бути сотні видач, і перевіряти кожну вручну довго.

## Завдання 4. Індекс і ORDER BY

Запит: `SELECT * FROM loans ORDER BY loan_date;`

- **До індексу на даті:** `SCAN loans` і другим рядком **`USE TEMP B-TREE FOR ORDER BY`**. SQLite читає всі рядки й окремо сортує їх у тимчасовій структурі.
- **Після** `CREATE INDEX idx_loans_date ON loans(loan_date)`: `SCAN loans USING INDEX idx_loans_date`.

Зник крок сортування (`USE TEMP B-TREE FOR ORDER BY`). Індекс уже зберігає значення `loan_date` у відсортованому порядку, тому SQLite просто читає рядки за індексом, і вони виходять у потрібному порядку без окремого сортування. Для `ORDER BY loan_date DESC` план такий самий, бо індекс можна читати і в зворотному напрямку.

## Завдання 5. DROP INDEX і повторна перевірка

Я видалив індекс командою `DROP INDEX idx_loans_reader;` і повторив запит із Завдання 1. План: **`SEARCH loans USING INDEX idx_loans_reader_returned (reader_id=?)`**.

До `SCAN loans` план не повернувся, бо в таблиці лишився композитний індекс `idx_loans_reader_returned(reader_id, return_date)`, який починається з тієї самої колонки `reader_id`. Індекс можна використовувати, коли умова стосується його першої колонки, тож композитний замінив видалений.

Перевірка видалення: `SELECT name, tbl_name FROM sqlite_master WHERE type = 'index';` показала три індекси (`sqlite_autoindex_readers_1`, `idx_loans_reader_returned`, `idx_loans_date`). Запит `... AND name = 'idx_loans_reader'` повернув 0 рядків, тобто індекс справді видалено.

## Відповіді на контрольні питання

1. `EXPLAIN QUERY PLAN` лише показує, як SQLite збирається виконати запит, і сам запит не виконує, тому результату не видно. План треба перевіряти окремо, бо запит дає однаковий результат з індексом і без нього: він «просто працює» в обох випадках, і різниця лише в швидкості. На малій таблиці цієї різниці не видно, тож без перегляду плану не зрозуміти, чи індекс узагалі використовується.
2. Індекс лише на `reader_id` допомагає знайти всі видачі читача, але другу умову (`return_date IS NULL`) SQLite змушений перевіряти вручну в кожному знайденому рядку. Композитний індекс на обох колонках використовує обидві умови одразу й одразу веде до потрібних рядків, тож додаткового перегляду менше.
3. Ціна індексу: він займає місце на диску, а також уповільнює `INSERT`, `UPDATE` і `DELETE`, бо при кожній зміні даних треба оновлювати й індекс. Тому не варто індексувати кожну колонку «про всяк випадок»: більшість індексів ніхто не використовуватиме, а витрати на місце й на запис лишаться. Індекс створюють цілеспрямовано, під запити, які реально виконуються часто.
